# Machine Learning

## Overview

The machine-learning component of the Building & Energy Intelligence Platform is designed as a short-horizon forecasting system for building energy consumption.

The current ML workflow is:

```text
BDG2 Data
   ↓
Data Validation
   ↓
Feature Engineering
   ↓
Baseline + Model Training
   ↓
Evaluation
   ↓
MLflow Experiment Tracking
   ↓
Model Registry
   ↓
Promotion / Rejection Decision
   ↓
Model Serving
   ↓
FastAPI Inference Service
   ↓
Application / Dashboard
   ↓
Monitoring
   ↓
Drift + Performance Detection
````

The ML layer is designed to demonstrate not only forecasting, but also the engineering lifecycle around a forecasting model:

* reproducible training
* baseline comparison
* time-aware evaluation
* model versioning
* model signatures
* candidate evaluation
* promotion gates
* safe fallback serving
* inference validation
* application integration
* prediction monitoring
* data-quality monitoring
* feature-drift detection
* model-performance monitoring
* degradation detection
* service-health observability

The current system is CPU-first and designed to run locally on a normal development laptop.

Phase 5 extends the ML lifecycle beyond model serving by adding observability and automated verification. It does not introduce automatic retraining.

# Prediction Target

The primary prediction target is:

```text
target_next_hour_kwh
```

The task is therefore a one-hour-ahead energy-consumption forecasting problem.

Conceptually:

```text
Historical Building Context
          +
Weather / Metadata
          ↓
Predict next-hour energy consumption
```

For a feature row associated with time `t`, the target represents the energy consumption at the next hourly step.

---

# Forecasting Horizon

The current model performs one-step-ahead hourly forecasting.

The serving contract requires historical observations immediately preceding the target timestamp.

The current inference service requires:

```text
168 consecutive hourly observations
```

This corresponds to:

```text
168 hours = 7 days
```

The historical window provides the model with enough context to construct the required lag and rolling features.

---

# Feature Engineering

The Phase 1 feature pipeline constructs features from:

* historical consumption
* weather
* building metadata
* calendar information
* temperature-derived demand indicators

The feature construction is designed so that the model receives information that would have been available before the prediction timestamp.

---

## Historical Energy Features

Historical electricity consumption is used to construct features such as:

* lagged energy consumption
* recent consumption patterns
* rolling energy statistics
* historical consumption context

These features provide information about the building's recent behaviour.

---

## Lag Features

Lag features represent previously observed energy consumption.

The inference service reconstructs these features from the historical observations supplied with the prediction request.

The conceptual relationship is:

```text
Energy(t-1)
Energy(t-2)
Energy(t-3)
...
Energy(t-168)
       ↓
Lag Features
```

This allows the model to use recent and weekly historical behaviour.

---

## Rolling Features

Rolling statistics summarize recent energy behaviour.

The feature pipeline includes rolling statistics such as:

* rolling means
* rolling maximums
* recent consumption summaries

Conceptually:

```text
Historical consumption
        ↓
Rolling window
        ↓
Summary statistic
        ↓
Model feature
```

These features help represent local changes in building consumption rather than relying only on individual lag values.

---

## Weather Features

Weather-related variables provide environmental context for energy consumption.

Weather information is incorporated into the feature dataset alongside building and temporal information.

The prediction-time request also contains weather context so that the inference service can reconstruct the expected feature representation.

---

## Building Metadata Features

The feature set incorporates building-level information such as:

* floor area
* primary use
* site information
* timezone
* building characteristics

These features provide relatively static context about the building being forecast.

---

## Calendar Features

Temporal features capture recurring consumption patterns.

These include:

* hour
* day
* weekday
* month
* other calendar-derived information

These features allow the model to represent recurring temporal behaviour.

---

## Heating and Cooling Features

Heating and cooling degree-hour style features are included to represent temperature-related building demand.

These features provide additional context when energy consumption is influenced by environmental conditions.

---

# Baseline Models

The project evaluates simple forecasting strategies before relying on learned models.

The primary baseline is persistence.

Persistence predicts the next hour using the most recently observed energy value.

Conceptually:

```text
Prediction(t + 1) = Energy(t)
```

The current baseline strategies include:

```text
pred_persistence
pred_previous_day
pred_previous_week
```

These baselines are intentionally simple.

Their purpose is to establish a meaningful reference against which learned models can be evaluated.

A more complex model is not automatically considered better simply because it uses more sophisticated algorithms.

---

# Persistence Baseline

The persistence strategy is:

```text
Use the latest observed energy value
as the next-hour prediction.
```

It is particularly important in this project because building energy consumption has temporal autocorrelation.

A learned model therefore needs to demonstrate that it provides useful improvement beyond simply carrying forward the latest observation.

# Evaluation Metrics

The current evaluation pipeline records multiple metrics.

These include:

* MAE
* RMSE
* CVRMSE
* NMAE
* macro-building NMAE

The metrics are recorded separately for validation and test evaluation where available.

---

## MAE

Mean Absolute Error measures the average absolute prediction error.

Conceptually:

```text
MAE = mean(|actual - prediction|)
```

It remains easy to interpret in the same general scale as the target.

---

## RMSE

Root Mean Squared Error gives greater influence to larger errors.

Conceptually:

```text
RMSE = sqrt(mean((actual - prediction)^2))
```

This makes it useful for detecting whether a model has large individual forecasting errors.

---

## CVRMSE

Coefficient of Variation of RMSE normalizes RMSE relative to the relevant energy scale.

The project records CVRMSE as a percentage.

---

## NMAE

Normalized Mean Absolute Error expresses absolute error relative to the relevant normalization scale.

It provides a normalized metric for comparing forecasting performance.

---

## Macro-Building NMAE

Macro-building NMAE aggregates building-level normalized performance so that individual buildings are not allowed to dominate the evaluation simply because they have larger consumption magnitudes.

This metric is important for the current model promotion logic.

The current learned-model promotion selection uses:

```text
validation_macro_building_nmae
```

# Baseline-Aware Promotion Guard

The project implements an explicit promotion guard.

The principle is:

```text
Best evaluated learned model
          ↓
Compare against baseline
          ↓
Does learned model beat baseline?
       ↙              ↘
     Yes               No
      ↓                 ↓
Eligible             Reject
for production       candidate
```

A learned model is not promoted merely because it is the best learned model.

It must also satisfy the baseline requirement.

# Building-Level Evaluation

The project uses macro-building metrics because the dataset contains multiple buildings with different consumption magnitudes.

A model can perform well on high-consumption buildings while performing poorly on smaller buildings.

Macro-building evaluation reduces the possibility that the largest buildings dominate the overall metric.

This is one reason:

```text
validation_macro_building_nmae
```

is used by the current learned-model promotion-selection logic.

Each successful prediction can be recorded with contextual information including:

```text

```

The monitoring state keeps a bounded in-memory history rather than storing an unlimited number of observations.

The current monitoring state is capped at:


This keeps the local application lightweight and predictable.

A monitoring observation represents a prediction event.

It should not be confused with:



Those are dataset characteristics rather than monitoring-event counts.

# Prediction and Outcome Observations

Prediction monitoring and performance monitoring use different levels of information.

A prediction record can be created when the system generates a forecast.

A performance observation requires the corresponding actual outcome to become available.

Conceptually:

```text
Prediction
    ↓
Prediction Record
```

and later:

```text
Prediction
+
Actual Outcome
    ↓
Performance Observation
```

Therefore, a system can have prediction observations without yet having enough outcome observations to calculate reliable performance metrics.

# Building-Level Performance Monitoring

Performance can be aggregated globally and by building.

The building-level view is important because aggregate performance can hide degradation concentrated in a subset of buildings.

The monitoring layer therefore supports:

```text
Global performance
+
Per-building performance
```

This extends the same building-aware philosophy already used by the model evaluation pipeline.

---

# Performance Windows

Performance monitoring uses bounded recent windows rather than requiring the entire historical monitoring state for every calculation.

The default recent window is:

```text
30 observations
```

Performance degradation is evaluated using sustained windows.

The current degradation configuration requires:

```text
30 observations per window
3 sustained windows
```

Therefore:

```text
30 × 3 = 90 outcome observations
```

are required before a sustained degradation decision can be evaluated under the default configuration.

This prevents a small number of unusual predictions from immediately causing a degradation decision.

---

# Performance Degradation Detection

The current degradation detector compares recent model performance against the configured reference condition.

The default relative degradation threshold is:

```text
10%
```

The detector requires sustained degradation across the configured number of windows.

Conceptually:

```text
Recent Outcomes
      ↓
Performance Windows
      ↓
Compare with Reference
      ↓
Window Degradation Signals
      ↓
Sustained Window Check
      ↓
Degradation State
```

Possible states include:

```text
insufficient_data
healthy
degraded
```

With the current configuration, fewer than 90 required outcome observations produce:

```text
insufficient_data
```

rather than a premature degraded state.

This is intentional.

---

# Baseline-Aware Performance Monitoring

Performance monitoring retains the persistence baseline alongside the served prediction.

This allows the system to distinguish:

```text
Model performance
```

from:

```text
Persistence baseline performance
```

Conceptually:

```text
Prediction + Actual
        ↓
Model Error

Persistence + Actual
        ↓
Baseline Error

Model Error
     vs
Baseline Error
```

This continues the baseline-aware philosophy used during model promotion.

A future learned model should not be considered healthy merely because its absolute error is changing; its performance should also be interpreted relative to the baseline and relevant reference window.

# Feature Drift Detection

Phase 5 introduces feature-distribution drift monitoring.

The current implementation uses Population Stability Index (PSI) as the drift measure.

Conceptually:

```text
Reference Distribution
        +
Current Distribution
        ↓
PSI
        ↓
Drift Status
```

The current thresholds are:

```text
PSI < 0.10
    → healthy

0.10 ≤ PSI < 0.25
    → warning

PSI ≥ 0.25
    → critical
```

The current minimum drift sample count is:

```text
30
```

If fewer than 30 current observations are available for a feature, the result is:

```text
insufficient_data
```

rather than a drift decision.

# Optional Input Handling

Monitoring instrumentation must not change the validity of an otherwise valid prediction request.

Optional weather fields may be absent.

The monitoring feature extraction therefore treats optional weather values safely rather than attempting to convert missing values directly to floating-point numbers.

This keeps observability instrumentation from becoming a failure point for the prediction path.

# Reference Profile

Drift detection compares current feature values against a reference profile.

The configured reference profile is:

```text
configs/monitoring_reference.json
```

The reference profile provides historical distributions against which current observations can be compared.

If a reference distribution is unavailable for a feature, the monitoring result reports:

```text
reference_unavailable
```

rather than inventing a drift value.

This distinction is important because:

```text
no reference
```

is not equivalent to:

```text
no drift
```

---

# Drift Interpretation

Drift is treated as a monitoring signal rather than an automatic retraining trigger.

The intended relationship is:

```text
Data Drift
     +
Data Quality
     +
Model Performance
     +
Service State
     ↓
Evidence Correlation
     ↓
Potential Lifecycle Action
```

A drift signal by itself does not imply that retraining is required.

This prevents the system from reacting to harmless distribution changes that do not actually reduce forecasting quality.

# ML Design Principles

The ML layer follows several core principles.

## 1. Baselines before complexity

A simple baseline must establish whether learned models add meaningful value.

## 2. Time-aware feature construction

Historical features must not use information unavailable at prediction time.

## 3. Training-serving parity

Inference must reconstruct the same feature semantics expected by the model.

## 4. Evaluation before deployment

A trained model is not automatically a production model.

## 5. Baseline-aware promotion

The strongest learned candidate must still justify replacing the baseline.

## 6. Preserve rejected candidates

Rejected models remain traceable in the registry.

## 7. Explicit serving state

The service reports whether it is serving a learned model or the baseline.

## 8. Reproducibility

Training configuration and relevant lifecycle metadata are tracked.

## 9. Model signatures as contracts

Registered model signatures provide a machine-readable input contract.

## 10. Local-first engineering

The ML system remains runnable on a normal CPU-oriented development environment.

## 11. Observable serving

Predictions, service state, drift, and performance should be observable without changing the serving decision automatically.

## 12. Evidence before retraining

Drift or an isolated prediction error should not independently trigger retraining.

## 13. Sustained degradation over isolated anomalies

Performance degradation should be supported by sufficient samples and sustained evidence.
