# Machine Learning

## Overview

The machine-learning component of the Building & Energy Intelligence Platform is designed as a short-horizon forecasting system for building energy consumption.

The current ML workflow is:

```text
BDG2 Data
   ↓
Data Validation
   ↓
Feature Engineering
   ↓
Baseline + Model Training
   ↓
Evaluation
   ↓
MLflow Experiment Tracking
   ↓
Model Registry
   ↓
Promotion / Rejection Decision
   ↓
Model Serving
   ↓
FastAPI Inference Service
   ↓
Application / Dashboard
````

The ML layer is designed to demonstrate not only forecasting, but also the engineering lifecycle around a forecasting model:

* reproducible training
* baseline comparison
* time-aware evaluation
* model versioning
* model signatures
* candidate evaluation
* promotion gates
* safe fallback serving
* inference validation
* application integration

The current system is CPU-first and designed to run locally on a normal development laptop.

# Prediction Target

The primary prediction target is:

```text
target_next_hour_kwh
```

The task is therefore a one-hour-ahead energy-consumption forecasting problem.

Conceptually:

```text
Historical Building Context
          +
Weather / Metadata
          ↓
Predict next-hour energy consumption
```

For a feature row associated with time `t`, the target represents the energy consumption at the next hourly step.

---

# Forecasting Horizon

The current model performs one-step-ahead hourly forecasting.

The serving contract requires historical observations immediately preceding the target timestamp.

The current inference service requires:

```text
168 consecutive hourly observations
```

This corresponds to:

```text
168 hours = 7 days
```

The historical window provides the model with enough context to construct the required lag and rolling features.

---

# Feature Engineering

The Phase 1 feature pipeline constructs features from:

* historical consumption
* weather
* building metadata
* calendar information
* temperature-derived demand indicators

The feature construction is designed so that the model receives information that would have been available before the prediction timestamp.

---

## Historical Energy Features

Historical electricity consumption is used to construct temporal features such as:

* lagged energy consumption
* recent consumption patterns
* rolling energy statistics
* historical consumption context

These features provide information about the building's recent behaviour.

---

## Lag Features

Lag features represent previously observed energy consumption.

The inference service reconstructs these features from the historical observations supplied with the prediction request.

The conceptual relationship is:

```text
Energy(t-1)
Energy(t-2)
Energy(t-3)
...
Energy(t-168)
       ↓
Lag Features
```

This allows the model to use recent and weekly historical behaviour.

---

## Rolling Features

Rolling statistics summarize recent energy behaviour.

The feature pipeline includes rolling statistics such as:

* rolling means
* rolling maximums
* recent consumption summaries

Conceptually:

```text
Historical consumption
        ↓
Rolling window
        ↓
Summary statistic
        ↓
Model feature
```

These features help represent local changes in building consumption rather than relying only on individual lag values.

---

## Weather Features

Weather-related variables provide environmental context for energy consumption.

Weather information is incorporated into the feature dataset alongside building and temporal information.

The prediction-time request also contains weather context so that the inference service can reconstruct the expected feature representation.

---

## Building Metadata Features

The feature set incorporates building-level information such as:

* floor area
* primary use
* site information
* timezone
* building characteristics

These features provide relatively static context about the building being forecast.

---

## Calendar Features

Temporal features capture recurring consumption patterns.

These include:

* hour
* day
* weekday
* month
* other calendar-derived information

These features allow the model to represent recurring temporal behaviour.

---

## Heating and Cooling Features

Heating and cooling degree-hour style features are included to represent temperature-related building demand.

These features provide additional context when energy consumption is influenced by environmental conditions.

# Baseline Models

The project evaluates simple forecasting strategies before relying on learned models.

The primary baseline is persistence.

Persistence predicts the next hour using the most recently observed energy value.

Conceptually:

```text
Prediction(t + 1) = Energy(t)
```

The current baseline strategies include:

```text
pred_persistence
pred_previous_day
pred_previous_week
```

These baselines are intentionally simple.

Their purpose is to establish a meaningful reference against which learned models can be evaluated.

A more complex model is not automatically considered better simply because it uses more sophisticated algorithms.

---

# Persistence Baseline

The persistence strategy is:

```text
Use the latest observed energy value
as the next-hour prediction.
```

It is particularly important in this project because building energy consumption has temporal autocorrelation.

A learned model therefore needs to demonstrate that it provides useful improvement beyond simply carrying forward the latest observation.

# Evaluation Metrics

The current evaluation pipeline records multiple metrics.

These include:

* MAE
* RMSE
* CVRMSE
* NMAE
* macro-building NMAE

The metrics are recorded separately for validation and test evaluation where available.

---

## MAE

Mean Absolute Error measures the average absolute prediction error.

Conceptually:

```text
MAE = mean(|actual - prediction|)
```

It remains easy to interpret in the same general scale as the target.

---

## RMSE

Root Mean Squared Error gives greater influence to larger errors.

Conceptually:

```text
RMSE = sqrt(mean((actual - prediction)^2))
```

This makes it useful for detecting whether a model has large individual forecasting errors.

---

## CVRMSE

Coefficient of Variation of RMSE normalizes RMSE relative to the relevant energy scale.

The project records CVRMSE as a percentage.

---

## NMAE

Normalized Mean Absolute Error expresses absolute error relative to the relevant normalization scale.

It provides a normalized metric for comparing forecasting performance.

---

## Macro-Building NMAE

Macro-building NMAE aggregates building-level normalized performance so that individual buildings are not allowed to dominate the evaluation simply because they have larger consumption magnitudes.

This metric is important for the current model promotion logic.

The current learned-model promotion selection uses:

```text
validation_macro_building_nmae
```

# Baseline-Aware Promotion Guard

The project implements an explicit promotion guard.

The principle is:

```text

          ↓

       ↙              ↘

      ↓                 ↓
Eligible            Reject

```

A learned model is not promoted merely because it is the best learned model.

It must also satisfy the baseline requirement.

# ML Design Principles

The ML layer follows several core principles.

## 1. Baselines before complexity

A simple baseline must establish whether learned models add meaningful value.

## 2. Time-aware feature construction

Historical features must not use information unavailable at prediction time.

## 3. Training-serving parity

Inference must reconstruct the same feature semantics expected by the model.

## 4. Evaluation before deployment

A trained model is not automatically a production model.

## 5. Baseline-aware promotion

The strongest learned candidate must still justify replacing the baseline.

## 6. Preserve rejected candidates

Rejected models remain traceable in the registry.

## 7. Explicit serving state

The service reports whether it is serving a learned model or the baseline.

## 8. Reproducibility

Training configuration and relevant lifecycle metadata are tracked.

## 9. Model signatures as contracts

Registered model signatures provide a machine-readable input contract.

## 10. Local-first engineering

The ML system remains runnable on a normal CPU-oriented development environment.
